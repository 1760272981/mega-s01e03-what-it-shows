Parser: the tenant writes the day first; the shared parser reads the month first

The shared parser reads month first regardless of the tenant’s date convention. For a day-first tenant, an input meaning 7 April can become 4 July. The affected group includes app and email reports, and form reports using the older booking form. Changing the visible hint alone does not repair this parsing path.

The parser ticket should make parsing follow an explicit, agreed date format and preserve the intended calendar date. It should test both ambiguous dates (where both numbers are valid months) and unambiguous dates, across the affected input channels. These are proposed acceptance checks; the export does not contain the production parser to patch or reproduce directly.

Form hint: what people are told to type disagrees with how the form reads it

For day-first tenants using booking-v3, form submissions are a separate hint group. The form displays MM/DD/YYYY, but reads the entry according to the tenant’s date order. A person following that hint can therefore get a different date despite following the instructions. Fix the hint and the form’s interpretation together; do not assume a parser fix elsewhere fixes it.

The form ticket should check the displayed instruction, the submitted value, and the resulting calendar date together for each affected tenant. App or email reports from those same tenants still belong to the parser group: tenant identity alone is not sufficient to classify the report.
